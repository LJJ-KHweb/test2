# 개발용 데이터베이스 구성

프로젝트에서 제공한 DDL을 기준으로 정리한 **Oracle용 신규 DB 생성 스크립트**입니다. 테이블·컬럼 순서, 자료형·길이, NULL 허용 여부, 기본값, PK·FK·UNIQUE 및 명시적 인덱스를 원본에 맞췄습니다. 기존 DB를 변경하는 마이그레이션 스크립트는 아닙니다. 다른 DBMS로 전환하는 경우 매퍼 SQL과 JDBC 설정도 별도로 변경해야 합니다.

## 파일 구성

| 파일 | 용도 |
| --- | --- |
| [schema.sql](schema.sql) | 제공된 DDL 기준 테이블 9개, 기본값, PK·FK·UNIQUE 제약조건, 인덱스 생성 |
| [seed.sql](seed.sql) | 일반 INSERT문으로 임시 관리자와 FK로 연결된 예시 데이터 생성 |
| [verify.sql](verify.sql) | 생성된 데이터 수와 필터링·추천 결과를 조회하는 확인용 SQL |

스크립트는 UTF-8로 저장되어 있습니다. DBeaver에서 Oracle 연결에 속한 SQL 편집기로 파일을 엽니다. SQL Developer, SQLcl, SQL*Plus도 사용할 수 있으며 클라이언트 인코딩을 UTF-8에 맞춥니다. 샘플의 `국&찌개`는 문자열 연결과 `NCHR(38)`로 구성해 SQL*Plus의 치환 변수 처리에 영향을 받지 않도록 했습니다.

### 원본에서 정리한 부분

- 붙여넣기 과정의 HTML 엔티티와 역슬래시 이스케이프를 제거했습니다.
- IDENTITY 옵션을 `GENERATED ALWAYS AS IDENTITY (START WITH 1 INCREMENT BY 1)` 형태로 정리했습니다. 내부 시퀀스는 Oracle이 관리하므로 `ISEQ$$` 시퀀스를 직접 생성하지 않습니다. [Oracle CREATE TABLE 문서](https://docs.oracle.com/en/database/oracle/oracle-database/21/sqlrf/CREATE-TABLE.html)
- 비밀번호·인증 설정이 빠진 `CREATE USER` 문은 테이블 스크립트에서 제외했습니다. DB 계정은 미리 준비합니다.
- 컬럼 주석의 `C##AO` 소유자 지정은 제거해 접속한 애플리케이션 스키마에 적용되도록 했습니다.
- 환경별 `STORAGE`, `TABLESPACE`, 물리 저장 옵션은 지정하지 않았습니다. 접속 계정의 기본 테이블스페이스를 사용합니다.

이전 코드 기반 초안에서 임의로 추가했던 CHECK 제약조건과 보조 인덱스도 원본 DDL에 맞춰 제거했습니다.

## 1. 빈 애플리케이션 스키마 준비

프로젝트에서 사용하는 Oracle 서비스와 애플리케이션 계정으로 접속합니다. 기존 계정이 `C##AO`라면 해당 계정에 연결하고, 새 환경에서는 별도로 준비한 계정을 사용합니다. 테이블 생성 권한과 기본 테이블스페이스 할당량이 필요합니다. SYS/SYSTEM 계정으로 실행하지 않습니다.

계정 생성과 권한 설정은 DB 환경에 따라 다르므로 이 파일에서는 수행하지 않습니다. `DB_USERNAME`에 설정할 애플리케이션 계정으로 접속한 상태에서 `schema.sql`을 엽니다. DBeaver에서는 **SQL 스크립트 실행(Alt+X)**으로 부모 테이블부터 순서대로 생성합니다. 각 문장을 병렬 실행하는 기능은 사용하지 않습니다. [DBeaver SQL 실행 안내](https://dbeaver.com/docs/dbeaver/SQL-Execution/)

SQLcl 또는 SQL*Plus에서 `db` 폴더를 작업 디렉터리로 사용하는 경우:

```sql
@schema.sql
```

SQL Developer에서는 파일을 열고 스크립트 실행(F5)을 사용할 수 있습니다.

빈 애플리케이션 스키마에서 한 번만 실행합니다. DROP이나 기존 데이터 삭제는 포함하지 않습니다. 대상 이름이 이미 있으면 해당 CREATE 문에서 오류가 발생하므로 오류 발생 시 실행을 중단하도록 클라이언트를 설정합니다. Oracle DDL은 자동 커밋되므로 중간 오류가 나면 앞서 생성된 객체는 남습니다. 재실행 전에 오류 원인과 이미 생성된 객체를 확인해야 합니다.

### 테이블 관계

| 테이블 | 주요 역할 및 관계 |
| --- | --- |
| `MEMBER` | 회원 정보. 아이디는 전체 회원 기준 고유 값 |
| `TOKEN` | `TOKEN_NO`를 PK로 사용. 토큰 값은 UNIQUE이며 앱에서 Refresh Token의 JTI와 밀리초 단위 만료 시간을 저장 |
| `MEMBER_ALLERGY` | 회원별 알레르기 재료. 같은 회원·재료 조합은 UNIQUE |
| `RECIPES` | 작성 회원을 참조하는 레시피 및 영양 정보 |
| `MATERIAL` | 레시피별 재료 및 분량 |
| `RECIPE_STEPS` | 레시피별 조리 단계. 레시피 내 단계 순서는 고유 값 |
| `BOOKMARK` | 회원 번호와 레시피 번호를 복합 PK로 사용하는 즐겨찾기 |
| `DEVICE` | 회원당 1개의 디바이스 |
| `STEP_LOG` | 디바이스별 누적 걸음 수 보고 기록 |

이메일·연락처는 원본의 `VARCHAR2(500)`, 해시 컬럼은 NULL을 허용하는 `VARCHAR2(64)`를 유지했습니다. 이메일·연락처 중복 여부는 활성 회원의 HMAC 해시로 검사하며, 해시 인덱스는 원본대로 단일 컬럼 인덱스입니다.

`MATERIAL.AMOUNT`는 `NVARCHAR2(45)`, `RECIPE_STEPS.STEP_INFO`는 `VARCHAR2(2000)`을 유지했습니다. 현재 API의 분량 검증은 최대 30자이므로 DB 길이와 다릅니다. `VARCHAR2`의 BYTE/CHAR 길이 단위는 원본에 명시되지 않아 생성 세션의 `NLS_LENGTH_SEMANTICS`에 따릅니다. 원본 DB와 동일한 한글 저장 범위가 필요하면 해당 설정도 확인해야 합니다.

대표 이미지명 `RECIPE_MAIN_IMG`와 경로 `RECIPES_IMG_PATH`는 모두 NOT NULL입니다. 샘플도 두 값을 반드시 넣으며, 조리 단계 이미지와 회원 프로필 이미지만 NULL을 허용합니다.

## 2. 임시 관리자 계정

`seed.sql`의 첫 INSERT문이 다음 계정을 생성합니다. 회원가입 API 호출은 필요하지 않습니다.

| 항목 | 값 |
| --- | --- |
| 아이디 | `admin` |
| 비밀번호 | `admin1234` |
| 권한 | `ROLE_ADMIN` |
| 이름 | 임시관리자 |

비밀번호는 Spring Security의 `BCryptPasswordEncoder`로 생성한 해시를 저장하며, `admin1234`와 일치하는지 검증했습니다. `ROLE_ADMIN` 계정을 생성해도 아직 구현되지 않은 관리자 API가 추가되는 것은 아닙니다.

연락처 `01000000000`과 이메일 `admin@example.com`은 개발용 평문 값이며, 현재 `AesUtil`의 기존 평문 호환 처리를 사용합니다. 실제 환경의 암호화 키를 사용하지 않으므로 `EMAIL_HASH`와 `PHONE_HASH`는 NULL입니다. 이 계정은 개인정보 암호화·연락처 중복 확인 테스트용으로는 사용할 수 없습니다. 해당 기능은 회원가입 API로 별도 계정을 만들어 검증합니다.

## 3. 예시 데이터 적용

스키마 생성 후 같은 DB 계정으로 `seed.sql`을 실행합니다. 파일은 일반 `INSERT INTO ... VALUES ...;` 문과 마지막 `COMMIT;`으로만 구성되어 있습니다. DBeaver에서는 **SQL 스크립트 실행(Alt+X)**으로 위에서 아래로 순서대로 실행합니다.

실행 전에 자동 커밋을 끄고, 첫 오류에서 실행을 중단하도록 설정합니다. SQLcl 또는 SQL*Plus에서는 오류 중단을 설정한 뒤 실행합니다.

```sql
WHENEVER SQLERROR EXIT SQL.SQLCODE ROLLBACK
@seed.sql
```

회원 번호·레시피 번호·디바이스 번호는 IDENTITY가 자동 생성합니다. 자식 INSERT문의 서브쿼리가 `admin`의 회원 번호와 해당 회원의 레시피·디바이스 번호를 조회하므로 ID가 1부터 시작하지 않아도 FK가 연결됩니다.

`admin`이 없는 개발 DB에서 한 번만 실행합니다. 이미 `admin`이 있으면 첫 INSERT문에서 아이디 중복 오류가 발생하므로 이후 문장을 계속 실행하지 않습니다. 기존 계정을 수정하거나 덮어쓰지 않습니다. DBeaver에서 중간 오류가 발생하면 실행을 중단하고 `ROLLBACK;`을 실행합니다. 마지막 `COMMIT;`까지 실행하면 삽입 내용이 확정됩니다.

| 데이터 | 생성 내용 |
| --- | --- |
| 회원 | 임시 관리자 `admin` 1명 |
| 알레르기 | 땅콩, 우유 |
| 레시피 | 총 6개. 650·700·750·690·710 kcal와 칼로리 미입력 레시피 |
| 재료·조리 단계 | 레시피별 재료 2개, 조리 단계 2개 |
| 즐겨찾기 | 닭고기 덮밥, 두부 채소밥 |
| 디바이스 | 회원에 연결된 디바이스 1개 |
| 걸음 수 | 이전 6일 각 1건과 오늘 2건, 총 8건 |

레시피의 재료·분량·칼로리·조리 단계는 기능 확인용 값입니다. 대표 이미지는 NOT NULL 제약을 충족하도록 `sample-placeholder.jpg`와 `https://example.com/allergy-out/sample-placeholder.jpg`를 넣습니다. 이 주소는 실제 이미지가 없는 예시 주소입니다. 화면에서 이미지까지 확인하려면 각 레시피 INSERT문의 이미지명·URL을 실제 테스트 이미지 값으로 바꿉니다. S3 객체는 이 스크립트에서 업로드하지 않습니다. Refresh Token은 샘플로 삽입하지 않고 실제 로그인 시 생성합니다.

## 4. 데이터 확인

DBeaver에서는 `verify.sql`의 SELECT 문을 하나씩 실행해 결과를 확인합니다. SQLcl 또는 SQL*Plus에서는 다음 명령을 사용합니다.

```sql
@verify.sql
```

이 파일은 데이터를 변경하지 않고 회원별 행 수, 필터 적용 결과, 한 끼 700 kcal 추천 결과, 일별 걸음 수를 조회합니다.

초기 데이터 적용 직후의 예상 결과는 다음과 같습니다.

| 확인 항목 | 예상 결과 |
| --- | --- |
| 전체 레시피 목록 | 6개 |
| `admin`의 알레르기 필터 적용 목록 | 4개. 땅콩버터 비빔면과 우유 감자수프 제외 |
| 하루 목표 2,100 kcal 추천 | 두부 채소밥(700), 닭고기 덮밥(650), 버섯 볶음밥(750) 순서 |
| 칼로리 미입력 과일 컵 | 목록에는 포함, 칼로리 추천에서는 제외 |
| 즐겨찾기 | 2개 |
| 오늘 걸음 수 기록 | 1,000걸음과 3,600걸음의 누적 기록 2개 |
| 최근 7일 기록 | 7일치. 오늘의 총 걸음 수는 최댓값인 3,600 |

위 개수는 다른 데이터가 없는 신규 DB 기준이며, 추천 순서는 조회수 등 데이터를 변경하기 전 기준입니다. 걸음 수의 오늘/최근 7일 기준은 매퍼와 동일하게 Oracle의 `SYSDATE`를 사용합니다. 날짜가 바뀌면 조회 범위와 결과도 달라집니다.

API까지 확인하려면 상위 [README](../README.md)의 설정으로 서버를 실행하고 `admin` / `admin1234`로 로그인합니다. 발급된 Access Token을 보내 레시피 목록, 칼로리 추천, 즐겨찾기, 일별·주간 걸음 수를 조회합니다. SQL 파일은 서버 시작 시 자동 실행되지 않습니다.

## 검증 범위

스키마는 제공된 DDL을 기준으로 정리했으며 샘플 데이터와 매퍼에서 사용하는 테이블·컬럼을 대조했습니다. 실제 Oracle 서버에서 스키마 생성, 데이터 삽입, 애플리케이션 연동까지 실행 검증한 상태는 아닙니다. 기존 DB에서 옮겨오는 경우에는 원본과 대상 DB를 비교해 별도의 마이그레이션을 준비해야 합니다.
